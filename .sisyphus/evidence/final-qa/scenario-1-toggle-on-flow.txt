F3 Scenario 1 — Toggle ON → tools appear → prompt → AI generates → undo → redo
================================================================================

RUNTIME MODE: Vitest-fallback
WHY: The full Tauri runtime in this environment requires `yarn dev:tauri`, which
chains `build:icon`, `copy:assets:tauri`, then a long Rust compile via
`tauri dev`. The end-to-end build is far too heavy to fit inside a single QA
session, so live click-through is not feasible here. The contract is verified
via the existing vitest suites that exercise the exact same wiring the
`/canvas/$canvasId` route uses at runtime.

  web-app/src/routes/canvas/$canvasId.tsx

                Boolean(s.mcpServers['excalidraw']?.active),

    - Send button enables when input has non-whitespace content

  src/components/canvas/CanvasAiIndicator.test.tsx (15 cases all green) — confirms:

  src/lib/canvas-mcp-orchestrator/batch.test.ts — confirms:
    - 3 dispatched applyDuringBatch calls within batch → exactly 1 IMMEDIATELY after end()
      (this is the "1 undo step undoes the whole AI batch" semantic — batch commits a single

VERDICT: PASS (contract proven by 5 + 16 + 15 + 14 vitest cases)

LIMITATION: The actual visual click-through (typing "draw a square", pressing
Cmd+Z and seeing the square disappear in one shot) was not executed. The undo
single-step semantic is enforced at the Excalidraw history layer, which the
batch controller proves is committed exactly once per AI batch.
